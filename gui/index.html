Primeiro uso

Monte uma avaliação reproduzível

Escolha uma task, configure os candidatos, revise a prévia efetiva e só então execute. Skills e juiz entram quando forem uma variável do experimento.

    Comparar modelos

    Mesmo agente e mesmas skills; duplique o candidato e altere apenas o modelo.

    Comparar agentes

    Mesma task e modelo quando compatível; adicione um perfil por agente.

    Avaliar skills

    Duplique uma baseline sem skills e altere apenas o conjunto de skills.

    Modo livre

    Combine dimensões quando a pergunta exigir; a prévia mostrará todas as diferenças.

    Novo experimento

    Rode a mesma task com combinações explícitas de agente, modelo e skills. A prévia mostra os valores efetivos antes de qualquer execução.

    Finalidade: manter o mesmo agente e as mesmas skills enquanto você varia o modelo. Exemplo: DeepSeek Flash contra Pro. Padrão: Comparar modelos. Obrigatório para orientar a montagem; não altera o Harbor sozinho.

    2. Montar candidatos

    Escolha um agent e clique "Adicionar" — o model e o skill set já vêm pré-preenchidos com o que está configurado nesse agent, mas você pode sobrescrever só nessa linha. Pode adicionar o mesmo agent mais de uma vez com overrides diferentes (ex.: mesmo agent, dois models diferentes).

    0 entradas adicionadas.

    3. Escolher task e volume

    Para começar, selecione evals/python/soma-fracoes, que tem teste e solução. Os seed-task são stubs para criar outras tasks.

    Configuração avançada

    "Jobs dir" é a pasta onde os resultados são gravados — use pastas diferentes pra não misturar comparações.

    4. Como rodar

    "n-attempts" repete cada combinação N vezes (reduz ruído). "Concurrency" roda combinações em paralelo — cuidado com custo de API se aumentar.

    —

    A estimativa vem do histórico de runs desta máquina (custo por trial já medido para aquele agent+model, × n-attempts × tasks × linhas) e aparece sozinha ao montar a comparação. Se passar do teto, a run é recusada e você escolhe: aumentar o teto ou confirmar. 0 = sem teto. Combinação nunca rodada não tem como ser estimada — nesse caso vale um limite de volume: acima de 5 trials pagos às cegas, também pede confirmação.

    ⚠ É uma guarda pré-voo, não um limite rígido: o harbor run desta versão não expõe flag de custo, então depois que a run começa nada aqui a interrompe se ela passar do estimado. Para limite real em execução, alguns adapters aceitam o próprio kwarg — ex.: --ak cost_limit=0.50 no campo "Extra harbor run args" com o mini-swe-agent.

    Argumentos avançados

    Aceita --timeout-multiplier e --ak/--agent-kwarg. Outros flags são recusados para não alterar modelo, task, tentativas ou volume por fora da prévia. Credenciais entram apenas por Credenciais.

    Chaves cadastradas em Credenciais são injetadas automaticamente nesta execução.

    "Cancelar" solicita a parada do processo harbor. Containers só são parados quando manifest, label, prefixo e identidade comprovam a propriedade. Containers do Harbor sem esses metadados são preservados; confira podman ps e os logs do job antes de qualquer limpeza manual.

    Agentes
    
      
    Um agente aqui é um perfil reutilizável do Harbor. Só nome e adaptador são obrigatórios; modelo, instruções e conjuntos de skills são opcionais e podem ser definidos depois.
    
      
    
        
        
    
          
    
          
    
        
    
        
    Comece a digitar para ver os … adapters registrados pelo Harbor 0.22.0 (o campo continua livre — dá pra passar um import path customizado). Model-agnostic (marcados na lista, ex.: mini-swe-agent, terminus-2, aider) aceitam o formato genérico provider/modelo; a compatibilidade concreta ainda depende do adapter e do provider. Os demais (claude-code, codex, gemini-cli…) são CLIs de um fornecedor específico e falam a API dele. oracle e nop não gastam API — bons pra testar o kit.
    

        
        

        
        
    Texto sempre anexado como uma skill a este agent (vira um SKILL.md interno). Pode escrever direto ou anexar um .md.
    
        
        
        

        
        
    Finalidade: preencher inicialmente os conjuntos de skills de um novo candidato deste perfil; em Novo experimento, você pode remover ou trocar essa seleção por candidato. As instruções do perfil continuam anexadas. Padrão: nenhum; opcional.

    Critérios do juiz
    
      
    Um critério é uma pergunta que um juiz responde PASS/FAIL/N-A sobre uma execução. Cadastre uma vez e reaproveite em vários conjuntos de critérios.
    
      
    
        
        
        
        
        
        
        
        
        
      
    
      
    
    
    
  
    

  
  
    
    
    
      
    Conjuntos de critérios
    
      
    Um conjunto agrupa perguntas de avaliação para reutilizar com um juiz em Novo experimento, numa task ou em Análise avulsa. No Harbor, esse pacote é chamado de rubric.
    
      
    
        
        
        
        
        
    Finalidade: definir quais perguntas PASS/FAIL/N-A fazem parte deste conjunto. Padrão: nenhum; opcional durante o cadastro, mas um conjunto vazio não pode ser usado para analisar.
    
        
    cadastre critérios primeiro, na aba "Critérios"
    
        
        
      
    
      
    
    
    
  
    

  
  
    
    
    
      
    Juízes
    
      
    Um juiz é o perfil que avalia resultados: adaptador, modelo, instruções e conjuntos de critérios padrão. Reaproveite-o em Novo experimento, Análise avulsa e no padrão de uma task.
    
      
    Sobre "skills": diferente do Agent, não dá pra anexar uma skill (SKILL.md) de verdade ao Judge — conferido no código do Harbor instalado (harbor/analyze/analyzer.py): o harbor analyze monta o agente avaliador sem nunca setar .skills, e o comando analyze não tem flag --skill (diferente do harbor run, que tem). O que dá pra fazer de verdade é reescrever as instruções do juiz por completo (abaixo) — é a única alavanca que o Harbor expõe pra moldar como ele avalia.
    
      
    
        
        
    
          
    
          
    
        
    
        
    O adapter executa o juiz no Harbor. Tasks tradicionais fornecem arquivos do trial; no modo repositório + PR, o juiz recebe somente os dois diffs, requisitos e checks sanitizados. Se escolher uma conexão de Credenciais abaixo, use o mesmo adapter configurado nela.
    

        
    Prazo de execução do juiz
    Padrão: 8 horas por tarefa do juiz. Aumente para specs longas; não há teto fixo de horas na plataforma. O prazo é congelado no lote e aplicado pelo Harbor somente ao agente juiz, sem incluir build ou instalação. Não há timeout externo de dois/dez minutos.
    
        
        
        
    A lista mostra modelos cadastrados em Modelos que constam da seleção high-tier do kit. Se estiver vazia, cadastre um destes: .
    
        
    
          
          
        
    

        
    Conjuntos de critérios padrão
    
        
    Finalidade: definir a seleção inicial quando este juiz for escolhido. Em Novo experimento e Análise avulsa, você pode alterá-la antes de rodar; a task também pode ter sua própria seleção. Ao iniciar um lote, a sessão congela a escolha final. Padrão: nenhum, que usa os critérios nativos do Harbor; opcional e permite vários.
    
        
    cadastre conjuntos primeiro, na aba "Conjuntos de critérios"
    

        
        
        
    Este é o texto padrão real do Harbor (harbor/analyze/prompts/analyze.txt do pacote instalado) — edite pra apertar o rigor, focar em algo específico, mudar o tom, etc. {trial_path}, {task_section} e {criteria_guidance} são preenchidos pelo Harbor automaticamente — mantenha esses três marcadores em algum lugar do texto, senão o juiz não recebe o caminho do trial nem a orientação dos critérios. Limpar o campo inteiro volta a usar o padrão do Harbor (não grava --prompt nenhum).

    3. Skills
    
      
    Uma skill é um conjunto de instruções que um agente pode receber. Escreva aqui, anexe um Markdown ou aponte para uma pasta existente; depois, agrupe skills em Conjuntos de skills.
    
      
    
        
        
        

        
        
    
          
          
        
    
        
    Finalidade: escolher entre criar a skill aqui ou apontar para uma pasta pronta. Exemplo: “Escrever instruções” para uma skill nova. Padrão: escrever instruções. Obrigatório; use pasta existente somente quando ela já contém SKILL.md.
    

        
    
          
          
          
          

          
          
    Confirmado no código do Harbor instalado (harbor/trial/trial.py, _upload_injected_skills): ele sobe a pasta inteira da skill pro ambiente do agente, não só o SKILL.md — a mesma convenção de "progressive disclosure" que Anthropic/OpenAI recomendam pra skills (o SKILL.md referencia o arquivo por caminho relativo, ex. "veja examples/bom.py", e o agente lê sob demanda). Anexe um ou mais arquivos — o nome do arquivo vira o caminho relativo dentro da skill; pode incluir uma subpasta no nome (ex. examples/bom.py) se você renomear o arquivo antes de anexar.
    
          
    
          
          
          
        
    
        
    
          
          
          
    Pode ter qualquer outro arquivo/subpasta além do SKILL.md (exemplos, templates, scripts) — Harbor sobe a pasta inteira pro agente, então tudo que estiver aqui vai junto.
    
        
    

        
        
      
    
      
    
    
    
  
    

  
  
    
    
    
      
    Conjuntos de skills
    
      
    Um conjunto agrupa uma ou mais skills para comparar como unidade ou vincular a um perfil de agente.
    
      
    
        
        
        
        
        
    Finalidade: definir as skills anexadas por este conjunto. Padrão: nenhuma; opcional durante o cadastro, embora um conjunto vazio não altere a execução.
    
        
    cadastre skills primeiro, na aba "Skills"
    
        
        
      
    
      
    
    
    
  
    

  
  
    
    
    
      
    Credenciais de providers
    
      
    Comece por aqui. Cadastre a chave de cada provider direto ou a chave de inferência de seu gateway LiteLLM — veja a seção opcional abaixo. Os models e agents das próximas abas mostram a credencial esperada. Gravadas localmente em secrets.env (state dir do kit), não como variável do Windows/sistema. São usadas apenas nas operações que precisam delas, como execuções, descoberta e testes explícitos. Escrita apenas — o valor nunca é mostrado de novo nem incluído nos exports.
    
      
    
        
        
        
    
          
    
          
    
        
    
        
    "Name" precisa ser exatamente o nome da variável de ambiente que o Harbor/LiteLLM espera pra aquele provider (maiúsculas, sem espaço — ex.: ANTHROPIC_API_KEY, OPENAI_API_KEY). Escolher um provider no dropdown acima já preenche isso certo pra você. "Value" é a chave em si, colada como está no painel do provider.
    
        
      
    
      
    Depois de salvar, o teste só roda quando você escolhe um modelo exato e clica Testar modelo escolhido. Ele faz uma pequena chamada paga. Descobrir modelos apenas consulta o catálogo do provider e não envia completion.
    
      
    
    
    
  
    

  
  
    
    
    
      
    Criar uma task
    
      
    Uma task é o problema que o agente tenta resolver em Novo experimento. Gere o esqueleto e depois complete instrução, ambiente, solução de referência e teste.
    
      
    
        
    
          
    
          
    
        
    
        
    Vira o nome da pasta da task (dentro do Output dir) e o identificador que aparece na lista abaixo e no seletor de task da aba Compare. "Org" é só um prefixo/namespace (ex.: minha-org/minha-task) — pode deixar em branco se o Name já tiver a barra.
    

        
    
          
    
          
    
        
    
        
    "Output dir" é onde a pasta da task vai ser criada em disco (ex.: .\evals\python\my-task) — é esse caminho que você depois cola no campo "Task / dataset path" da aba Compare. "Steps" define se a task é de um passo só (0 — o normal: 1 instruction.md, 1 test.sh) ou de N passos sequenciais (gera steps/step-1/, steps/step-2/, ... cada um com sua própria instruction.md e test.sh; se um passo falhar, os seguintes não rodam). Use N>0 só se a task representa um fluxo de várias etapas dependentes — na dúvida, deixe 0.
    

        
        
        
        
        
    Description e Author são só metadados gravados no task.toml da task (aparecem pra quem for ler/reusar a task depois) — não afetam a execução.
    

        
    
        
    
        
    Por padrão o esqueleto já vem com um tests/test.sh de exemplo baseado em pytest e um solution/solve.sh de referência — marque pra pular um deles se for escrever o seu do zero num formato diferente (ex.: teste não-Python, ou task sem solução de referência).

    Datasets
    
      
    O que é: um pacote publicado de tasks prontas. Quando usar: para avaliar candidatos num benchmark conhecido. Quando pular: ao usar apenas tasks próprias.
    
      
    Como usar: 1) baixe um dataset pelo nome (form abaixo); 2) as tasks dele aparecem sozinhas em datasets/<nome>/<task>/ — o mesmo escaneamento que lista suas tasks próprias (aba Tasks) também lista essas, e elas entram automaticamente no seletor de task da aba Compare. Não existe um "modo dataset" separado: depois de baixado, uma task de dataset se comporta exatamente como uma task sua.
    
      
      
    Este botão só imprime um link pro Hub do Harbor (catálogo de datasets publicados) — nesta versão do Harbor o CLI ainda não lista os nomes disponíveis diretamente no terminal, então é preciso abrir esse link no navegador pra descobrir o nome exato do dataset que você quer baixar. Limitação do `harbor dataset list` em si, não desta UI.
    
      
    
        
    
          
    
          
    
        
    
        
    O nome vem do link do Hub acima (não tem preenchimento automático — copie o nome exato de lá). "Output dir" é a pasta onde as tasks baixadas vão ficar; o padrão "datasets" é o que a aba Tasks/Compare já sabe escanear — só troque se tiver um motivo específico pra organizar em outro lugar.
    
        
      
    
      
    
      
    
    
    
  
    

  
  
    
    
    
      
    Config Bundle — compartilhar configuração de avaliação entre máquinas
    
      
    O que é: Agentes, Modelos, Skills, Conjuntos de skills, Critérios, Conjuntos de critérios e Juízes vivem em ~/.harbor-eval-kit/, por máquina — sem isto, um time não consegue versionar essa configuração em git, revisar em PR, nem garantir que todos usam as mesmas definições. Credenciais nunca entram aqui — um Modelo é só um rótulo + provider/modelo, nunca uma chave.
    
      
    Como usar: "Exportar" baixa um .json com tudo — commite esse arquivo no repo do time. Quem for aplicar clica "Importar" e escolhe o arquivo. É idempotente por id: importar o mesmo bundle de novo atualiza em vez de duplicar, e um item que só existe localmente (não veio do bundle) nunca é apagado.
    
      
      
    
        
        
      
    
      
    
    
    
  
    

  
  
    
    
    
      
    Logs das execuções
    
      
    O que é: os arquivos de log que o próprio harbor grava dentro do jobs dir enquanto (e depois que) uma run acontece — job.log do job inteiro, trial.log de cada tentativa, a saída bruta do agent e a do verificador. Quando usar: pra acompanhar uma run em andamento (a aba Compare fica esperando sem detalhar o que está acontecendo), ou pra investigar depois por que uma linha deu erro. Diferença pra "Trajectories": lá você vê a trajetória estruturada do agent (turnos, ferramentas, edições) no viewer do Harbor; aqui é o log cru de execução, incluindo build da imagem, instalação do agent e o teste rodando — que é onde falha de container/rede/dependência aparece.
    
      
    
        
    
        
    
      
    
      
      
      
    
        
        
      
    
      
      
    
      
    
    
    
  
    

  
  
    
    
    
      
    Visualizador de trajetórias
    
      
    O que é: um segundo servidor web (do próprio Harbor, não desta GUI) que abre numa aba nova e mostra, passo a passo, tudo que o agent fez dentro do container numa run: comandos executados, arquivos lidos/editados, saída de cada ferramenta, a resposta do modelo em cada turno. É a evidência bruta por trás do número de reward. Quando usar: depois de rodar uma comparação em Novo experimento, quando o reward sozinho não explica o suficiente — reward baixo e você quer ver onde o agent travou, reward alto e você quer confirmar que não foi um atalho/gambiarra, ou só quer entender o estilo de trabalho de um agent específico. É complementar à análise por juiz (Análise avulsa ou painel de resultados): o juiz dá um veredito resumido; aqui você vê a trajetória inteira com os próprios olhos, sem intermediário.
    
      
    Como usar: aponte para a mesma pasta de jobs usada no experimento (o botão "Ver trajetórias" já traz esse caminho) e clique "Iniciar visualizador". A preparação mostra tempo, estado e log; a URL só é aberta depois que o Harbor informa um endereço HTTP local válido. O processo continua ativo até você clicar "Parar".
    
      
    
        
        
        
      
    
      
    
      
    Visualizadores ativos
    
      
    Cada linha é um harbor view ainda rodando. Clique "Parar" quando terminar para liberar a porta. Falhas ao iniciar ou parar permanecem visíveis com a mensagem real.

Use para uma inspeção ad hoc; no fluxo normal, prefira Analisar junto aos resultados de Novo experimento.
    
      
    
        
        
        
        
        
        
        
        
    Finalidade: escolher os grupos usados nesta inspeção. Padrões do juiz são apenas uma pré-seleção editável. Cada conjunto marcado gera uma chamada paga separada ao modelo juiz; sem marcação, usa reward_hacking + task_specification do Harbor.
